# «Zoom to Fit» и режим оптимизации зума — протокол RE

Наука за модулем `fitfill`. Статус-журнал: `batch-2026-11-17-status.md`.

---

## 1. Симптом

После Ctrl+D / «Zoom to Fit» деталь занимает ~35 % ширины и ~45 % высоты
окна, центр смещён вправо-вниз; повторное нажатие ничего не меняет
(скриншоты друга, подтверждено пользователем).

## 2. Ложный след (документирован, чтобы не наступать повторно)

Цепочка QML `fitView()` → `Sn3DCanvasView::fitView` → `FitOperationAuto`
проверена другом живьём и НЕ является множителем для пункта меню:

- константа `3.5` @ RVA 0x25F8C0 (librenderkit.extensions.digit,
  `SceneCamera::fit`): 3.5→1.6 дала +4 п.п. по высоте;
- `3.5` @ RVA 0x293524 (librenderkit, функция дистанции 0x180050990 из
  `FitOperationAuto`): 3.5→1.3 — визуально без изменений.

Его финальная правка была одной байтой: `librenderkit.extensions.digit.dll`,
файловое смещение `0x171D68`, `01`→`00` (эталон r8; побайтовое сравнение
чистого и финального файла — отличий больше нет). Семантику он не объяснил,
смещение версионно-зависимо.

## 3. Семантика байта (3.1.x, наша разведка)

Байт на том же месте жив: код в файле —

```
... 48 85 C0 0F 84 05 01 00 00  B2 01 48 8B C8  FF 15 96 FA 0C 00 ...
                                  ^^
                     mov r10b, 1   (DL-аргумент №4 = bool true)
                     mov rcx, rax  (this = манипулятор)
                     call [rip+0xFA96]  → IAT-слот
```

Разбор потребовал двух проверок:

- **дельта file↔RVA**. Экспорт `?fitView@Sn3DCanvasView@...` имеет RVA
  `0x171560`; его пролог (`40 57 48 83 EC 50 ...`) лежит в файле на
  `0x170960` — дельта **.text: RVA = file + 0xC00** (наивный просмотр файла
  «по RVA» показывает на чужой байт и даёт ложную цель у `FF 15`).
  Значит байт кода на file `0x171D68` = RVA `0x172968`, внутри
  `Sn3DCanvasView::init` (Ghidra: функция начинается ~`0x172070`).
- **RIP-relative цель `FF 15`**. disp32 `0x0CFA96` от следующего за вызовом
  RVA даёт слот `0x180242408` (RVA `0x242408`). `dumpbin /imports` thunk-и по
  адресам не печатает — таблица импорта разобрана руками из DataDirectory[1]
  (ILD/INT, поимёнка):

```
0x242400  librenderkit.dll  ?getRotateCenter@CustomizeManipulator@@...
0x242408  librenderkit.dll  ?setIsZoomOptimization@CustomizeManipulator@@QEAAX_N@Z
0x242418  librenderkit.dll  ?isMouseInGizemoFitRegion@CustomizeManipulator@@...
```

Итог: `init` включает манипулятору «оптимизацию зума» — режим зафиксированной
дистанции камеры, из-за которого fit и не вписывает габарит. Сеттер/геттер
(Ghidra, librenderkit.dll, экспорты 0x56820/0x51930):

```c
void CustomizeManipulator::setIsZoomOptimization(bool v) { this[0x138] = v; }
bool CustomizeManipulator::getIsZoomOptimization()       { return this[0x138]; }
```

Единственный обнаруженный вызов — тот самый `init`. Байт-правка друга =
`mov r10b, 0` для одного места; наш эквивалент — тот же эффект для **всех**
вызывающих.

## 4. Реализация (`modules/fitfill`)

Детурн `host->hook` на экспортируемом сеттере (имя
`?setIsZoomOptimization@CustomizeManipulator@@`, уникальность проверяется
`ex_findExport`), форвард фиксированного `force` (ini, default 0 = режим
выключен). По имени, не RVA; поле `this[0x138]` руками не пишется — все
записи идут через штатный сеттер. `needsSiblings`: 3D-вью рендерятся и в
sibling-процессах.

Live (2026-11-17): `fitfill: hooked ... forcing value 0`,
`setIsZoomOptimization(1) -> forwarding 0` ×5 (создания вью), пользователь
подтвердил: Ctrl+D вписывает модель.

## 5. Принятый риск и откат

Режим оптимизации — дефолт вендора; глобальное выключение может изменить
ощущение интерактивного зума. В финальной редакции друга это lived, жалоб
нет; лог показывает каждый форс. Откат: `force = 1` (вендорово значение) или
`enabled = 0`, ничего на диске.
